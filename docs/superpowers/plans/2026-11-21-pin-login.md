# PIN Login Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Hosts sign in with email + 5-digit PIN; email is sent only for "forgot PIN"; 5 wrong PINs lock the account 15 minutes.

**Architecture:** Pure PIN helpers in `src/lib/domain/pin.ts` (rules + HMAC password derivation). A migration adds a private lock table and two key-guarded `SECURITY DEFINER` RPCs. Server actions in `src/app/login/actions.ts` orchestrate Supabase auth + the RPCs; `/login` becomes a 3-step card and `/login/new-pin` handles the reset link.

**Tech Stack:** Next.js 16 server actions, Supabase Auth (`signUp`, `signInWithPassword`, `resetPasswordForEmail`, `updateUser`), Postgres plpgsql, `node:crypto`, Vitest + Testing Library.

**Spec:** `docs/superpowers/specs/2026-11-21-pin-login-design.md`

## Global Constraints
- PIN: exactly 5 ASCII digits; reject all-same and straight ascending/descending runs.
- Supabase password = hex `HMAC-SHA256(PIN_SECRET, lowercased email + ":" + pin)`.
- `PIN_SECRET` is server-only (never `NEXT_PUBLIC_`), ≥32 chars; actions fail closed (`"failed"`) if it's missing or short.
- Lock: 5 consecutive failures → `locked_until = now() + interval '15 minutes'`; success or reset clears.
- RPCs require `p_key` with `sha256(p_key)` equal to the stored hash; wrong key raises.
- Every action trims + lowercases the email, validates format, applies `isHostEmailAllowed`.
- All new copy exists in `en` and `ar`.

## Review Focus
1. Locked account submitting the right PIN → still refused with minutes left (Task 3 test).
2. Email with capitals/spaces in step 1 vs step 2 → same account and same lock row (Task 3 test).
3. Supabase "invalid credentials" vs network error → only wrong PIN counts as a failure (Task 3 test).
4. Reset link opened, then `/login/new-pin` without a session → redirect to `/login`, no crash (Task 4 test).
5. PIN field pasted with spaces / Arabic-Indic digits `١٢٣٤٥` → normalized to ASCII before validation (Task 1 test).

### Task 2: Lock table + RPCs (migration)

**Files:** Create `supabase/migrations/0004_pin_login.sql`; Modify `supabase/tests/rls_smoke.sql` (add cases 7–7e)

**Interfaces — Produces (SQL, callable by `anon` and `authenticated`):**
- `public.pin_check(p_key text, p_email text) returns table(account_exists boolean, locked_until timestamptz)` — `account_exists` = a non-anonymous `auth.users` row with that lowercased email.
- `public.pin_record(p_key text, p_email text, p_ok boolean) returns timestamptz` — returns new `locked_until` (null if not locked).
- Tables: `private.pin_attempts(email text primary key, failures int not null default 0, locked_until timestamptz)`, `private.app_secrets(name text primary key, value_hash text not null)`; schema `private` with no grants to anon/authenticated.
- Key check: `encode(extensions.digest(p_key,'sha256'),'hex') = (select value_hash from private.app_secrets where name='pin_key')`, else `raise exception 'forbidden'`.

- [ ] **Step 1:** smoke cases: 7 wrong key raises; 7b four failures → not locked; 7c fifth → `locked_until` ≈ now()+15m; 7d `pin_check` reports lock; 7e success clears row. Insert a test hash inside the smoke transaction.
- [ ] **Step 2:** apply migration to the live project (`apply_migration`), run smoke via `execute_sql` → every line `ok`.

### Task 3: Server actions

**Files:** Modify `src/app/login/actions.ts` (replace `sendMagicLink`); Create `src/lib/supabase/pin-rpc.ts`; Test `tests/unit/login-actions.test.ts`

**Interfaces:**
- Consumes: Task 1 helpers; Task 2 RPCs.
- Produces:
  - `type LoginError = "invalid" | "domain_not_allowed" | "failed" | "wrong_pin" | "format" | "weak" | "mismatch"`
  - `checkEmail(email): Promise<{ status: "new" | "existing" } | { locked: number } | { error: LoginError }>` (`locked` = whole minutes left, ≥1)
  - `createAccount(email, pin, confirm): Promise<{ ok: true } | { error: LoginError }>` — `mismatch` when pins differ; existing email → `failed`.
  - `signInWithPin(email, pin): Promise<{ ok: true } | { locked: number } | { error: LoginError }>`
  - `sendPinReset(email, origin): Promise<{ ok: true } | { error: LoginError }>` — redirect `${origin}/auth/callback?next=/login/new-pin`; returns ok even for unknown emails.
  - `setNewPin(pin, confirm): Promise<{ ok: true } | { error: LoginError }>` — needs a session; clears lock via `pin_record(.., true)`.

- [ ] **Step 1: tests** (mock `@/lib/supabase/server` with a fake client recording calls; set `process.env.PIN_SECRET`):

  - network error (`{ error: { code: "unexpected_failure" } }`) → `failed`, `pin_record` NOT called.
  - locked (`pin_check` → `locked_until` 10 min ahead) with the right PIN → `{ locked: 10 }`, `signInWithPassword` NOT called.
  - fifth failure where `pin_record` returns a time → `{ locked: 15 }`.
  - `"  Host@X.com "` → RPC and auth both receive `host@x.com`.
  - `createAccount` with `12345` → `weak`, mismatch → `mismatch`, valid → `signUp` gets `pinPassword(secret,email,pin)`.
  - missing `PIN_SECRET` → `failed`.
